## A1 positivos, negativos, frontera y error
- GitHub Actions instala Node 24 y checkout completo con `fetch-depth:0`, `contents:read` y `persist-credentials:false`. El script exige `CI=true`, `GITHUB_SHA` de 40 dígitos y `git rev-parse HEAD` idéntico; verifica árbol limpio y existencia del commit origen.
- Crea un worktree `--detach` dentro del directorio temporal del runner en el **SHA de la prueba**; `git revert --no-commit` se ejecuta exclusivamente en ese worktree. Comprueba exactamente tres rutas staged, sin rutas inesperadas, y compara los tres blobs resultantes con el padre del SHA (3/3). Destruye solo el worktree temporal y revisa que el checkout original conserve HEAD y status.
- Tests `node --test`: control positivo de allowlist; negativos para incluir migración/datos tenant; bordes vacío/duplicado/faltante/extra; entradas adversariales como `../secrets`, null o valor no-array. Tests capaces de fallar si la validación permite una cuarta ruta.
- Cualquier salida inesperada, HEAD distinto, error de Git, falta de commit, lista alterada o blob divergente **falla el job**; nunca se degrada a PASS por un check de estado SKIPPED, CANCELLED o IN_PROGRESS.

## A2/A3 aplicación real y limitaciones
Integración real requerida: `git worktree`, `git revert`, index/staging y blobs del repositorio completo, **sin mocks**. El dominio de reversión ensayado se restringe a cambios de test/documentación, sin modificar runtime JWT/RBAC, API, Angular ni EF/MySQL: las pruebas HTTP/JWT/MySQL nuevas para este ensayo son **NO_APLICA**. La ausencia de escritura SQL implica que datos legítimos permanecen intocados **en este runner**; NO demuestra rollback de operaciones comerciales, migración MySQL, restauración de backups, servicio externo, despliegue ni dispositivo físico. Esos riesgos R2/R3 requieren microtareas separadas y autorización adicional. Los fallos históricos de CI permanecen intactos.
