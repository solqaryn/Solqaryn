## V26 — Seguridad de errores de mutación HTTP (DEV05, 23 noviembre 2026)

- **Hallazgo causal P1/R2:** el helper `manejarErrorMutacion` exponía directamente `err.error.message` en el DOM cuando el backend devolvía un error de escritura, pudiendo mostrar trazas SQL, tokens, datos de otro tenant o detalles internos. Esto contradecía el requisito de mensajes seguros de PLAN D239, aunque los estados de GET ya ocultaban el cuerpo de error. No se supone que el backend real filtre siempre su respuesta.
- **Corrección mínima runtime:** para fallos de PUT/logo se muestra solamente el mensaje seguro local proporcionado por la operación. HTTP 409/412 conserva la ruta de conflicto/recarga existente; no se alteran endpoints, permisos, JWT, EF, SQL ni mutaciones legítimas. `lastSaved` y exclusión `saving()` permanecen intactos.
- **Prueba adversarial real de interfaz:** sobre login de administrador JWT firmado y permiso efectivo de edición en MySQL 8.4 efímero, se intercepta únicamente el PUT para inyectar respuestas HTTP 403 y 500 con marcador de traza/tenant B. Se comprueba mensaje seguro, ausencia del marcador en `body`, formulario no expuesto tras el error y un único PUT; no se falsifica un rechazo de autorización del backend. La prueba queda pendiente de GitHub-hosted CI exact-SHA antes de concluir A0–A4.
- **Riesgo y límites:** R2 por posible exposición PII/tenant en errores de escritura, sin cambio de autorización ni integración SQL de producción. A5 requiere otra Task Javier distinta del autor/reparador. Rollback: revert normal de este commit sobre dev, preservando CI, V17 y bitácora. No QA/main/PROD.

## V27 — Revocacion reactiva de capacidad Editar tras montar formulario (23 noviembre 2026)

**Defecto P2/R2 causal:** el formulario de configuracion consultaba `PermisosRuntimeService.puede('Configuracion', 'Editar')` solamente en `ngOnInit` y almacenaba un `signal` estatico; un refresh, cambio de empresa o revocacion dejaba habilitados campos/acciones existentes aunque el backend siguiera denegando escrituras. Ahora `puedeEditar` es `computed` que lee las señales de permisos y tenant, y un `effect` habilita/deshabilita el formulario ya montado sin emitir eventos de valor. Las tres respuestas exitosas de mutacion (PUT, logo POST, logo DELETE) vuelven a exigir el permiso vigente antes de aplicar datos o emitir toast. No se cambian JWT, SQL, RBAC backend ni grants.

Este test modela la reactividad de la UI; **no** acredita revocacion JWT real, membresia MySQL, seguridad HTTP ni E2E completo. La suite GitHub-hosted de configuracion tenant prueba por separado JWT A/B, MySQL 8.4 efimero y Playwright.
