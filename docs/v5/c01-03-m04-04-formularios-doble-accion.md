## V30 — untrusted HTTP 200 success=false receipts (23 noviembre 2026)

**Brecha funcional R2:** en guardar, subirLogo y eliminarLogo se aceptaba una respuesta HTTP 200 con empresaId igual a la empresa efectiva aun cuando el propio contrato `ApiResponse.success` fuese `false`. Esto permitia anunciar exito, aplicar una version no confirmada y mostrar datos potencialmente obsoletos. La barra HTTP no certifica que una mutacion haya sido aceptada por el servidor.

**Correccion en el runtime Angular:** las tres mutaciones exigen ahora `success === true` antes de admitir el payload de la empresa o mostrar confirmaciones. Un recibo `success=false`, ausente o malformado pasa a `unconfirmed` y exige volver a consultar el estado remoto, sin repetir el PUT/POST/DELETE automaticamente ni conservar una afirmacion falsa de exito. La comprobacion independiente de `empresaId` sigue bloqueando datos de otra empresa. No se cambia API, DTO, JWT, permisos, EF, MySQL ni contratos de autorizacion del servidor.

**Regresion dirigida:** el unitario de Angular comprueba que `success=false` con empresaId A y una version falsamente mas reciente NO actualiza el formulario, NO abre snackbar, bloquea reintento hasta consulta y no muestra detalles privados del recibo. Los checks de compilacion, Vitest, Scope Lock y V5 pertenecen al SHA nuevo y no se declaran PASS sin readback; las pruebas E2E reales JWT/MySQL/Chromium se reusan solo si los archivos causales permanecen identicos y la equivalencia se acredita.
