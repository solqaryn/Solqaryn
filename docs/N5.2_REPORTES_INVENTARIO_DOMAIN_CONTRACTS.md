# N5.2.B.1 — Contratos transversales de dominio/query para Reportes de Inventario

## Alcance

QA_TAKEOVER de `N5.2.B.1.inventario_REPORT_DOMAIN_CONTRACTS` después de que ATTEMPT1 agotó el presupuesto de lane sin patch y quedó superseded/ownership revoked. Esta faceta posee sólo el envelope transversal: filtros comunes, paginación/orden, metadatos de resultado y fronteras de compatibilidad. No redefine valorización/Kardex, reconciliación, topology, QA ni RBAC.

## 1. Envelope común

Se materializa `ReporteInventarioFiltroBaseDto : PagedRequest` con los campos transversales mínimos:

- `Desde` / `Hasta`;
- `SucursalId`;
- `AlmacenId`;
- `UbicacionAlmacenId`;
- paginación, búsqueda y orden heredados de `PagedRequest`.

El default analítico es `SortBy=Fecha`, `SortDirection=desc`. Cada reporte especializado debe limitar `SortBy` a una whitelist propia y añadir únicamente filtros de su semántica, por ejemplo producto/variante, tipo de movimiento u origen de reconciliación.

## 2. Semántica temporal y paginación

- `Desde` es inclusivo (`>=`) y `Hasta` es inclusivo (`<=`), en continuidad con las consultas operativas existentes de movimientos. La capa de implementación debe normalizar/validar el contexto temporal antes de consultar y rechazar rangos invertidos.
- `PagedRequest` conserva `Page >= 1` y `PageSize` limitado a `1..200`.
- `SortDirection` sólo admite semántica `asc|desc`; valores no admitidos deben fallar validación, no traducirse a SQL dinámico arbitrario.
- Para datasets con timestamps repetidos, el repositorio especializado debe añadir un tie-breaker determinista, normalmente `Id`, sin cambiar la semántica primaria de la faceta.

## 3. Scope físico y seguridad

`SucursalId`, `AlmacenId` y `UbicacionAlmacenId` son filtros solicitados, no autoridad de acceso. La implementación siempre los intersecta con el scope autorizado. `UsuarioIdScope`, heredado de `PagedRequest` y marcado `JsonIgnore`, sigue siendo un dato interno fijado por servicio y nunca aceptado desde HTTP.

La política exacta de permisos, costo sensible, auditoría y fail-closed pertenece a N5.2.B.6 y no se duplica aquí.

## 4. Metadatos de resultado

El contrato transversal reutiliza `PagedResult<T>` como envelope de resultado paginado (`Items`, `Page`, `PageSize`, `TotalCount`, `TotalPages`). No se crea un segundo wrapper de paginación para N5.2.

Metadatos específicos de un reporte —por ejemplo moneda, método de costeo, flags de censura o snapshot de filtros efectivos— deben añadirse a un DTO especializado cuando sean materialmente necesarios; no se fuerzan dentro de `PagedResult<T>` si no son comunes a todas las familias.

## 5. Compatibilidad y no duplicación

- `MovimientoInventarioQueryDto`, `TransferenciaInventarioFiltroDto`, `ConteoInventarioQueryDto` y `AjusteInventarioFiltroDto` continúan siendo contratos operativos; no se reemplazan ni rompen.
- Los nuevos filtros analíticos deben heredar/componer `ReporteInventarioFiltroBaseDto` en lugar de copiar de nuevo período + scope físico + paginación.
- La UI no debe conocer ni coordinar múltiples DTOs operativos para construir una sola analítica transversal.
- Las facetas J1/J3 pueden añadir sus campos especializados sin apropiarse del envelope común.

## 6. Acceptance para N5.2.C+

La implementación posterior deberá aportar pruebas de:

1. binding/serialización del envelope y defaults;
2. rechazo de rangos invertidos y sort no permitido;
3. paginación estable y tie-break determinista;
4. intersección de filtros físicos con scope autorizado;
5. compatibilidad de `PagedResult<T>` y de los endpoints operativos existentes.
