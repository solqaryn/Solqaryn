## Ciclo productivo REVIEW_FIRST → RECOVER → CLAIM
1. En cada ocurrencia, aplicar Skill local vigente y contrastar repositorio+arquitectura, Scope Lock del HEAD de dev, Plan autorizado, GitHub, CONFIG y Sheets, permisos y `TASK_ID` reales. Primero certificar por FIFO los PR ya MERGED que aún estén VALIDANDO, siempre con posmerge 3/3 y readback institucional. Un scope puede cerrar múltiples PR ajenos, uno a uno, sin cuota artificial.
2. Para integrar, ordenar TODOS los PR OPEN dirigidos a dev por `created_at` ascendente, empatando por número, **no por fecha de commit**. Procesar un PR a la vez y refrescar `dev`, HEAD, revisiones y checks antes de cualquier escritura. Si el primero es propio, no revisarlo/fusionarlo/certificarlo; generar handoff a otra Task y seguir con PENDIENTE elegible. Si está bloqueado, no integrar PR posteriores.
3. Un branch detrás de dev no equivale por sí solo a conflicto: `behind>0` no es veto ni obliga a reconciliar cada commit. Solo hacer merge normal/no forzado a la rama ORIGINAL cuando exista conflicto REAL, una necesidad de integración demostrable, un gate exact-SHA o una protección que lo requiera. Verificar diff, tests y nuevo HEAD. Cada merge aprobado mueve dev y puede dejar otras ramas por detrás: no afirmar que 1000 PR pueden estar todos permanentemente delante. No cambiar branches ajenas en lote.
4. En PR comercial ordinario, una única Task distinta de la autora original y de cualquier contribuyente al HEAD final ejecuta **tres auditorías independientes por dimensión, no por actor** EN LA MISMA CORRIDA: A) funcional (alcance, pruebas causales, dependencias, contratos, UX/regresiones); B) seguridad (multiempresa, JWT/RBAC, privilegios, datos/PII, negativos, secretos); C) integración (FIFO por PR, HEAD y diff final, CI, migraciones/infra por impacto, documentación y rollback). Registrar PASS/FAIL y evidencia específica en GitHub sobre SHA exacto; N/A requiere motivo. Una revisión válida equivale a 1/1, nunca exigir 2/2 de rutina. Tres lecturas idénticas no constituyen tres auditorías.
5. Si el revisor corrige código en ese PR, pasa a ser contribuyente y ya no puede certificar independientemente el nuevo HEAD: otro TASK_ID elegible debe efectuar la revisión final triple. Para gobernanza, Skills, controles de seguridad, CI/workflows, scripts/security o PR exigidos por ruleset, conservar aprobación formal REAL de cuenta GitHub independiente de todos los contribuyentes; COMMENTED técnico no sustituye APPROVED formal. No usar dos logins para fingir un tercero.
6. Con revisión triple independiente válida, CI premerge required SUCCESS en HEAD final, `COLA!G=SI` por fórmula y rulesets correctos, fusionar protegido el primer PR a dev. Posmerge comprobar: A) MERGED y dev apuntan al MERGE_SHA; B) Scope Lock/Seguridad/Backend requeridos 3/3 SUCCESS exact MERGE_SHA; C) `PLAN_MAESTRO!H=LISTO`, `COLA!E=LISTO/G=SI` fórmulas intactas, `BITACORA` evento idempotente y readback; después sincronizar Jira KAN-4. Si posmerge pendiente, registrar `MERGED_CI_PENDING` y NO LISTO.
7. Cuando el primero está bloqueado por CI pendiente, permisos, dependencia o autor propio, NO esperar haciendo polling ni adelantar otro merge. Registrar diagnóstico causal deduplicado y tomar una microtarea `PENDIENTE` elegible del Plan con `COLA!O=SI`, responsable libre y predecesora en VALIDANDO o LISTO; registrar `EN_PROGRESO`, desarrollar, probar y entregar `VALIDANDO` con rama/PR real y autor original preservado. `COLA!O=SI` abre DESARROLLO, `COLA!G=SI` abre MERGE/LISTO solo al cumplir predecesoras LISTO. En falta de trabajo elegible, reportar bloqueo específico, no inventar entregas.
8. En CI fallida leer logs del job y corregir causa concreta. Ante `OTHER_CHECKS_PENDING`, verificar los nombres bloqueantes; reejecutar solamente Scope Lock fallido UNA vez después de que los checks relevantes terminen SUCCESS, sin volver a ejecutar checks verdes. GitHub Actions continúa. Clasificar suites caras por impacto sólo con clasificador fail-closed vigente y tests de seguridad, no omitir MySQL ante DB/migraciones/ambigüedad.
